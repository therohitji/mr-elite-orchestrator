1.0 PRINCIPLES (WHY THIS CONTRACT LOOKS LIKE THIS)
============================================================
A) Snapshot is NOT full history
Snapshot (state_data) must stay small and fast to update.
Full history belongs to workflow_state_events (Step 2/3).
B) Deterministic resume requires explicit pointers
We must always know:
- where we are (current_node)
- what to do next (next_actions or next_nodes_candidate)
- what has already happened (tool call receipts, approvals, event pointers)
C) Every mutable structure must be versioned
We will evolve state_data. schema_version is mandatory.
No version = broken migrations later.
D) Everything critical must be idempotent
Tool actions must never run twice accidentally.
We store receipts with idempotency keys and external ids.

2.5 DETERMINISTIC ORDERING (SEQUENCE VS TIMESTAMP)
============================================================
Never trust timestamps alone.
Two events can share same millisecond.
Network retries can reorder inserts.
So every session must have a monotonic sequence:
- sequence: bigint
- unique(session_id, sequence)
How to assign sequence safely
- in a transaction:
select max(sequence) + 1 where session_id = X
insert event with that sequence
- or maintain a per session counter in workflow_states
Edge case
Two workers append at same time:
- unique constraint rejects one
- retry logic re-reads max and tries again

4.0 SECURITY MODEL (LOCK THIS BEFORE WRITING POLICIES)
============================================================
We enforce these security truths:
Truth A: A user can only read data for orgs they belong to
Truth B: A user can only write data for orgs they belong to
Truth C: For states and events, client writes are risky
Recommended: client can read, but ONLY backend service role can insert or update
Why backend-only writes are recommended
- Prevents malicious or buggy clients from corrupting states
- Prevents users from forging approvals and tool receipts
- Keeps idempotency and sequencing reliable
So we implement:
- SELECT allowed for org members
- INSERT and UPDATE allowed ONLY for service role (or optionally org members if you insist)
- DELETE almost always blocked (service role only)

============================================================

Guarantee E: Writes are retry-safe

6.7 TRANSACTION DESIGN (HOW TO DO THIS WITHOUT CORRUPTION)
============================================================
Critical writes must be transactional.
Transaction T1 (append_event)

Otherwise two inserts can get same sequence.
Transaction T2 (tool wrappers)
- tool_called insert must commit BEFORE calling external tool
Because the tool call can succeed even if your server dies.
Transaction T3 (checkpoint_snapshot)
- use optimistic concurrency with version
Prevents overwriting newer snapshots written by another worker.
Edge case: insert succeeds but checkpoint fails
- event log still has truth
- snapshot will be repaired by replay or by a “snapshot reconciler” job

b) if external id known, fetch status from tool
c) if uncertain, require human approval before retry

Truth D: Lock acquisition must be atomic.
Truth E: If lock is lost, worker must STOP immediately.
This implies a lease-based locking mechanism stored in Postgres.

8.4 ACQUIRE LOCK (ATOMIC UPSERT PATTERN)
============================================================
Function: acquire_lock(session_id, workspace_id, worker_id) -> {lock_token, locked_until} or fail
Rule
- You acquire lock if:
a) no lock row exists for session_id
b) OR existing lock is expired (locked_until < now())
c) OR existing lock is held by you with same token (re-entrant renewal)
Atomic logic (conceptual)
- try insert
- if conflict, update only if expired
- if update affected 0 rows, you failed to acquire
You MUST return a unique lock_token to the worker.
The worker must include lock_token on every write afterwards.
Why lock_token matters
- If lock expires and another worker acquires it,
the old worker must not be allowed to continue writing checkpoints.
============================================================
8.5 RENEW LOCK (HEARTBEAT)
============================================================
Function: renew_lock(session_id, worker_id, lock_token) -> ok/fail
Rules
- renew only if lock_token matches current row
- extend locked_until = now() + lease_seconds
- update heartbeat_at = now()
If renew fails
- worker must STOP immediately
- because it lost the lock (someone else acquired it)
============================================================
8.6 RELEASE LOCK (CLEAN EXIT)
============================================================
Function: release_lock(session_id, worker_id, lock_token) -> ok
Rules
- delete row OR set locked_until = now() (expire it)
- only if lock_token matches
- do not allow a worker to release a lock it doesn’t own
Recommendation
Expire instead of delete if you want debugging:
- set locked_until = now(), keep row and metadata
But primary key constraint means 1 row always exists anyway.
Simplest: delete the row.

============================================================
Critical rule
Any backend operation that mutates session state must require:
- session_id
- lock_token
Writes include
- append_event
- checkpoint_snapshot
- begin_tool_action
- finish_tool_action
- request_approval
- decide_approval
Why
This prevents a dead worker from continuing to write after losing lock.
Implementation pattern
- When worker starts, acquire_lock -> get lock_token

8.8 EDGE CASES (REAL WORLD FAILURE MODES)
============================================================
Edge Case A: Worker crashes mid-session
- lock is not renewed
- locked_until expires
- new worker acquires lock and resumes safely from snapshot + events
Edge Case B: Network partition causes renew failures
- worker loses lock
- must stop
- another worker may acquire
This prevents split-brain execution.
Edge Case C: Long external tool call blocks renew
- worker must renew in a separate async timer thread while tool call is in progress
- if cannot renew, pause session for safety (or mark recoverable error)
Edge Case D: Two workers start at same time
- only one acquires lock due to atomic upsert
- other backs off and retries later
Edge Case E: Worker continues writing after losing lock
- prevented by lock_token gating
- DB or API rejects writes
Edge Case F: Locked session stuck forever
- lease expiration prevents permanent deadlocks
- admin override endpoint can force expire lock (service role only)
============================================================
8.9 BACKOFF + RETRY STRATEGY (SO WORKERS DON’T HAMMER DB)
============================================================
When lock acquisition fails
- wait random jitter 200ms to 1500ms
- retry limited times
- if still fails, exit and let scheduler retry later
For high throughput
- use a queue scheduler that only assigns unlocked sessions

8.11 RPC FUNCTIONS (RECOMMENDED) FOR ATOMIC ACQUIRE/RENEW
============================================================
Supabase best practice is to implement lock logic in RPC to keep it atomic.
RPC 1: acquire_workflow_lock(session_id, workspace_id, locked_by, lease_seconds)
- tries insert
- if conflict, updates only if expired
- returns lock_token and locked_until if acquired
- returns null if not acquired
RPC 2: renew_workflow_lock(session_id, lock_token, lease_seconds)
- updates locked_until only if lock_token matches
- returns success boolean
RPC 3: release_workflow_lock(session_id, lock_token)
- deletes row only if lock_token matches
- returns success boolean
Why RPC
- you guarantee atomicity inside DB
- you avoid race conditions from application-side multi queries
