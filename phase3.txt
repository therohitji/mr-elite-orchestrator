Phase 3 (Security)
This is Phase 3: The Control Layer.
Think of the Logic Layer as the "Business Manager" (checking permissions) and the Control Layer as the "Security Guard"
(checking safety).
Even if the Manager says "Open the door," the Security Guard will stop you if you are carrying a weapon.
Here is the technical blueprint for building the Control Layer.
1. The Architecture: The Middleware Pipeline
We do not write a monolithic "Check Everything" function. We build a Middleware Pipeline. The Atom must pass through a
series of "Filters" one by one. If it fails any filter, it is dropped.
The Pipeline Flow:
1. Input: Validated Atom (Green/Yellow status).
2. Filter 1 (Privacy): "Does this leak PII (passwords, SSN)?"
3. Filter 2 (Security): "Is this a Prompt Injection attack?"
4. Filter 3 (Reliability): "Is the API rate-limited? Is the system healthy?"
5. Filter 4 (Cost): "Does this execution exceed the token budget?"
6. Output: Verified Atom $\to$ Execution Layer.

3. The Master Controller (The Logic)
This is the function that runs the pipeline. It is the single entry point for Phase 3.
The Algorithm:
1. Sequential Check: Run Privacy $\to$ Security $\to$ Reliability.
2. Fail Fast: If any check returns False , stop immediately. Do not run the next check.
3. Audit Log: Record why it was blocked (for the Evaluation Layer later).
The Code ( core/control/engine.py ):

def run_control_layer(atom):
checks = [scan_privacy, scan_security, check_limits]

if not passed:
# STOP EVERYTHING

If the user asks something illegal or strictly forbidden, we should kill it immediately, before we even spend compute on

Here is the Optimized Architecture to solve both your questions: How Search Works and How to Stop Waste Early.
1. The Efficiency Fix: The "Pre-Flight" Guardrail
To stop "unwanted token wasting," we add a Layer 0: The Input Guardrail.
This runs before Mr. Elite even starts planning.
The Logic:
Instead of checking policy on the Atoms (late stage), we check policy on the Raw Prompt (early stage).
The "Fast Check" Algorithm (Layer 0):
1. Input: User Prompt ("Fire the CEO").
2. Action: Instant Vector Search against Global Policies (High-level rules).
3. Result: Found Rule: "Termination of C-Level execs requires Board Approval."
4. Decision: BLOCK immediately.
5. Cost: ~50 tokens (Fast & Cheap).
6. Saving: Saved ~2,000 tokens of Planning & Atomization logic.

2. The Logic Layer: How "Search & Analyze" Actually Works
For requests that pass the "Pre-Flight" check (e.g., "Draft a contract" - generic intent is safe, but specific details might
violate rules), we use the Logic Layer on the Atoms.
Here is the exact Vector Search & LLM Analysis Algorithm:
Step A: The Search (Finding the Rule)
Phase 3 (Security)
4We don't search using keywords (like SQL). We use Semantic Search (Embeddings).
Mechanism:
1. Convert Atom to Math: The system takes the Atom's description ("Draft offer for $160k") and sends it to an
Embedding Model (e.g., OpenAI text-embedding-3-small ).
2. Result: It returns a vector (a list of numbers: [0.12, -0.98, 0.05...] ).
3. Compare: The Vector Database (Pinecone) calculates the Cosine Similarity (angle distance) between this vector
and your stored Policy Vectors.
4. Retrieve: It pulls the top 3 rules that are mathematically "close" in meaning.
Step B: The Analysis (The Judge)
Just finding the rule isn't enough. We need to know if we broke it.
Atom: "Draft offer for $160k."
Found Policy: "Offers > $150k require approval."
The "Analysis" Algorithm:
We send a tiny prompt to a fast LLM (GPT-4o-mini) to act as the Comparator.

Plaintext
Context:
- Action: "Draft offer for $160k"
- Rule: "Offers > $150k require approval"
Question: Does the Action violate the Rule?
Output: { "violation": true, "reason": "160k > 150k" }
