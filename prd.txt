0) WHAT MR ELITE IS (FOR DEVELOPERS)
───────────────────────────────────────────────────────────────────────────────
Mr Elite is NOT “a chatbot”.
Mr Elite is a closed-loop orchestration runtime that converts vague user intent
into safe, atomic, policy-compliant actions (“ExecutionAtoms”), then executes them
through tools/agents/workflows, and finally learns from outcomes.
Core philosophy:
Decision First → Validate → Control/Secure → Execute → Evaluate/Learn
Key output contract:
Input : Raw user prompt (+ workspace + active employee/agent context)
Output : A DAG of ExecutionAtoms + execution results + logs + analytics + learned rules
Why this matters:
Your product’s “autonomy” is not magic.
It’s strict contracts + deterministic gates + human escalation + idempotent execution.

9) EDGE CASES YOU MUST HANDLE (REALITY CHECKLIST)
───────────────────────────────────────────────────────────────────────────────
A) Missing resource/template
- template not found → FAIL atom → replanning loop → ask user/upload
B) Ambiguous policy match
- vector similarity mid-range (e.g., 0.6–0.8) → do NOT guess
- escalate for human review or request clarification
C) Prompt injection in tool content
- email/slack message contains instructions to override system
- strip/ignore hostile text; switch to “summarize only” for that content
D) High-risk actions without explicit approval
- payments, offer letters, external emails, firing people
- must pause + show what will happen + require explicit confirmation
E) Tool failure and retries
- Gmail rate-limited → retry with backoff; if repeated, pause and notify user
- Calendar conflict → replan with alternative slots
F) Duplicate execution
- user clicks “run” twice, network retries, worker restart
- idempotency via atom.id prevents double-send/double-pay
G) Partial completion
- scheduling succeeded but rejections failed
- state must reflect partial results and next steps must be resumable
H) Infinite replanning loops
- cap replans, escalate to user with: “Blocked because X. Provide Y to continue.”
I) Cost explosion
- large inbox + huge attachments
- reliability guard should estimate cost and ask user to narrow scope
