GeniOS: Technical Architecture Specification
Version: 1.0 (MVP)
System: "Mr. Elite" – The Autonomous Orchestration Engine
Objective: To build a decision-aware execution layer that translates vague user goals into safe, atomic, and policy-
compliant actions 1111.
1. High-Level Architecture
The system is designed as a closed-loop pipeline consisting of five distinct phases. It follows the philosophy: "Decision
First, Execution Last"2.
The Data Flow Pipeline:
1. Input: Raw User Prompt.
2. Phase 1 (Planning): Classify $\to$ Reason $\to$ Atomize.
3. Phase 2 (Reasoning): Enrich (Policy + Resources) + Contextualize (Memory).
4. Phase 3 (Control): Security Guardrails + Privacy Filters.
5. Phase 4 (Execution): Dispatch to Tools/Agents via Hardcoded Registry.
6. Phase 5 (Evaluation): Analytics + Learning Loop (The Moat).
2. Phase 1: The Planning Layer
Goal: Convert ambiguity into structured "Atoms of Thought."
2.1. Component: Input Guardrail (Layer 0)
Function: pre_flight_check(prompt)
Logic: Vector Search against "Block List" policies.
Algo: Cosine Similarity > 0.85 = Immediate Block.
Purpose: Prevent token waste on illegal/impossible requests.
2.2. Component: Classification Engine
Logic: Semantic Routing via System Prompt.
Categories: CHAT (Conversational), QUERY (RAG), TASK (Atomic), GOAL (Composite) 3.
Output: Pydantic Object ( IntentClassification ).
2.3. Component: Chain of Thought (CoT) Engine
Logic: ReAct Pattern (Reason + Act). Generates a dependency graph.
Algorithm: Topological Sort (identifies which steps block others).
Constraint: Must output a list of dependencies (e.g., "Step B waits for Step A").
2.4. Component: Atomizer (The Structuring)
Logic: Converts text plans into the Atom JSON schema.

3. Phase 2: The Logic & Context Layer
Goal: Validate Atoms against business rules and fetch required assets 4.
3.1. Architecture: Parallel Enrichment
Mechanism: asyncio.gather() runs Logic and Context threads simultaneously.
3.2. Thread A: The Logic Engine (Policy + Resources)
Policy Logic:
Search: Vector Embedding Search (Pinecone) for relevant rules.
Judge: LLM-based audit ("Does Action X violate Rule Y?").
Decision Matrix:
Hard Violation $\to$ BLOCK.
Soft Violation + High Risk $\to$ ESCALATE (Yellow Light).
No Violation $\to$ APPROVE.
Resource Logic: Exact Key Match to fetch templates/files from Object Storage.
3.3. Thread B: The Context Engine (Memory + State)
State Logic: SQL Lookup (Supabase) for binary statuses (e.g., budget_open=true ).
Memory Logic: Vector Search for historical preferences ("Last time, User rejected this draft").
4. Phase 3: The Control Layer
Goal: Final security and reliability checkpoint before execution.
4.1. Middleware Pipeline
The Atom passes through a sequential chain of filters:
1. Privacy Guard: Regex scan for PII (SSN, Emails, API Keys). Redacts or Blocks.
2. Security Guard: Heuristic scan for Prompt Injection attacks.
3. Reliability Guard: Rate Limit check (Redis counters) and Cost Estimation.
4. Final Gate: If status == PAUSED (from Logic Layer), hold for Human API Approval.
5. Phase 4: The Execution Layer
Goal: safely execute the validated action.
5.1. Component: Central Dispatcher
Logic: Reads atom.tool_name and routes via TOOL_REGISTRY .
Routing Logic:
Type: CODE_TOOL $\to$ Execute Python Function immediately (Fast).
Type: AI_AGENT $\to$ Spin up Sub-Agent LLM Session (Slow/Creative) 5.
Type: WORKFLOW $\to$ Trigger LangGraph Sub-graph.
5.2. Safety Mechanisms
Hard Timeouts: All executions wrapped in timeout=30s .

6. Phase 5: The Evaluation Layer
Goal: The "Moat" – Self-learning and optimization 6.
6.1. Analytics Engine
Action: Logs cost, latency, and tool success rates to analytics_db .
6.2. Learning Loop (Implicit Feedback)
Trigger: When a user edits an output (e.g., rewrites an email).
Algo: Diff Analysis (Original vs. Final).
Action: Extracts a new "Preference Rule" and updates the Vector DB.
